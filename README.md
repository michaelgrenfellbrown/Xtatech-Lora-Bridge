# Xtatech LoRa Bridge

Reads data from a USB/serial LoRa receiver, publishes it to an MQTT broker, and provides a web interface for status, configuration, diagnostics, and a local terminal.

## 1. Prepare a fresh Linux installation

These instructions target Debian, Ubuntu, or Raspberry Pi OS with `apt` and `systemd`. The installer does not support other distributions unchanged.

You need:

- A regular Linux user account with `sudo` access. Log in as that user and run the commands below; do not start from a root shell, because the installer uses `SUDO_USER` to select the service account.
- Internet access to download system packages, the repository, and Python dependencies.
- A connected USB/serial LoRa receiver and its baud rate (default: `115200`).
- An existing, reachable MQTT broker, including its address, port, and credentials. The installer installs MQTT command-line clients, but does **not** install a broker.

If using a Raspberry Pi, install Raspberry Pi OS, configure networking and your user account, and enable SSH during OS setup if you intend to administer it remotely.

Install the tools used in this guide:

```bash
sudo apt update
sudo apt install -y git nano
```

## 2. Download the project

Use this exact checkout location if you want to use the web interface's repository installation feature later:

```bash
mkdir -p "$HOME/Downloads"
git clone https://github.com/michaelgrenfellbrown/Xtatech-Lora-Bridge.git "$HOME/Downloads/Xtatech Lora Bridge"
cd "$HOME/Downloads/Xtatech Lora Bridge"
```

If you already copied the full project folder onto Linux, change into that folder instead. The installer needs the Python files, `requirements.txt`, `config.yaml`, and the `web` directory beside `install.sh`; downloading only `install.sh` is insufficient.

Normalize Windows line endings before running the shell scripts:

```bash
sed -i 's/\r$//' install.sh uninstall.sh generate-local-https-cert.sh
```

Always run the installer with `bash`, not `sh`. Using `sudo bash install.sh` also avoids needing to make the file executable.

## 3. Configure the bridge before installation

The installer copies this configuration into `/opt/xtatech-lora-bridge/config.yaml` and immediately starts the service.

```bash
nano config.yaml
```

In nano, save with `Ctrl+O`, press Enter, then exit with `Ctrl+X`.

Edit the existing YAML sections; do not add duplicate sections. Preserve indentation using spaces.

### MQTT

Replace the supplied broker address and example credentials with your own. Choose a unique `client_id` and `gateway_id` if running more than one bridge:

```yaml
mqtt:
  host: "192.168.1.7"
  port: 1883
  username: "YOUR_MQTT_USERNAME"
  password: "YOUR_MQTT_PASSWORD"
  client_id: "xtatech-lora-bridge"
  base_topic: "lora"
  qos: 0
  retain: false
  gateway_id: "pi-zero2-gw01"

  discovery:
    enabled: false
    prefix: "homeassistant"
    expire_after_s: 7200
    republish_interval_s: 3600
```

The IP address above is an example, not a broker provided by this project. If your broker allows anonymous connections, use empty strings for the username and password. To use Home Assistant MQTT discovery, enable the existing `mqtt.discovery.enabled` setting and configure Home Assistant's MQTT integration to use the same broker.

### Serial receiver

The default automatically searches for a serial device:

```yaml
serial:
  port: "auto"
  baud: 115200
  timeout_s: 1.0
  reconnect_delay_s: 2.0
```

If several serial devices are connected, select the receiver explicitly. List persistent device paths with:

```bash
ls -l /dev/serial/by-id/
```

Set `serial.port` to the full path shown, or use a device path such as `/dev/ttyACM0` or `/dev/ttyUSB0`. Use the baud rate required by your receiver.

### Disable automatic reboots while setting up

The supplied configuration enables a watchdog that can reboot the machine after 900 seconds (15 minutes) without serial bytes, even if the serial port exists. During initial setup, change the existing setting to:

```yaml
watchdog:
  enabled: false
  no_serial_data_s: 900
  require_port_missing: false
  reboot: true
```

Enable it later only if automatic reboots suit your receiver's normal transmission interval.

### Web access

The defaults listen on all network interfaces at port `8088` and use the local HTTPS certificate generated by the installer:

```yaml
web:
  host: "0.0.0.0"
  port: 8088
  ssl_certfile: "certs/local.crt"
  ssl_keyfile: "certs/local.key"
  require_token: false
  token: "changeme"
```

Keep access on a trusted local network. The default web interface does not require a token and includes administrative operations. If enabling `web.require_token`, replace `web.token` with a strong private value. The local terminal has a separate token; the installer generates it when the configured terminal token is empty or `changeme`.

## 4. Install and start the service

From the project folder, run:

```bash
sudo bash install.sh
```

The installer:

- Installs Python 3, virtual environment support, pip, Git, OpenSSL, CA certificates, MQTT clients, and NetworkManager.
- Copies the application and configuration into `/opt/xtatech-lora-bridge`.
- Creates a Python virtual environment and installs `requirements.txt`.
- Generates a self-signed HTTPS certificate and configures the local terminal token.
- Adds your user to the `dialout` group for serial access.
- Disables system sleep, disables NetworkManager Wi-Fi power saving, and restarts NetworkManager. A remote connection may briefly drop.
- Adds `usbcore.autosuspend=-1` to the Raspberry Pi boot command line when a supported boot command-line file exists.
- Grants the service user passwordless access to the reboot command and to the installer at the expected Downloads checkout path.
- Enables and starts the `xtatech-lora-bridge` systemd service, including automatic startup after reboot.

After a successful installation, reboot once to apply group membership and any boot configuration change:

```bash
sudo reboot
```

## 5. Open and verify the bridge

After reconnecting, check the service and find the machine's LAN IP address:

```bash
sudo systemctl status xtatech-lora-bridge --no-pager
hostname -I
```

Open `https://<LINUX_IP>:8088` in a browser, replacing `<LINUX_IP>` with the machine's LAN address. For example: `https://192.168.1.50:8088`.

The generated certificate is self-signed, so a browser certificate warning is expected. Check that you are connecting to your own machine before accepting the certificate. If a firewall is enabled, allow TCP port `8088` from the trusted LAN using that firewall's configuration.

Useful pages:

| Path | Purpose |
| --- | --- |
| `/` | Main bridge interface |
| `/diagnostics` | Serial and application diagnostics |
| `/services` | Service and repository controls |
| `/metrics` | System metrics |
| `/ssh` | SSH status |
| `/terminal` | Local shell terminal; requires its separate terminal token |

The SSH page does not install an SSH server. If remote SSH access is required, enable it separately in your OS.

Check recent application logs:

```bash
sudo journalctl -u xtatech-lora-bridge -n 100 --no-pager
```

Confirm the interface reports a working serial connection and MQTT connection. To watch published MQTT data, substitute your broker details:

```bash
mosquitto_sub -h YOUR_BROKER_IP -p 1883 -u 'YOUR_MQTT_USERNAME' -P 'YOUR_MQTT_PASSWORD' -t 'lora/#' -v
```

Omit `-u` and `-P` for an anonymous broker. This command exposes credentials in the command arguments and potentially shell history; use a test account where appropriate. Press `Ctrl+C` to stop. With the default base topic, parsed node state is published to `lora/<node_id>/state`.

## 6. Change configuration after installation

The running service reads the installed copy, not the checkout's copy:

```bash
sudo nano /opt/xtatech-lora-bridge/config.yaml
sudo systemctl restart xtatech-lora-bridge
sudo systemctl status xtatech-lora-bridge --no-pager
```

The web interface also provides configuration controls. Keep a private backup of the active configuration, which contains MQTT credentials and terminal tokens:

```bash
mkdir -p "$HOME/xtatech-backups"
chmod 700 "$HOME/xtatech-backups"
sudo cp /opt/xtatech-lora-bridge/config.yaml "$HOME/xtatech-backups/config.yaml"
sudo chown "$(id -un):$(id -gn)" "$HOME/xtatech-backups/config.yaml"
chmod 600 "$HOME/xtatech-backups/config.yaml"
```

Repeat the backup before updates if configuration has changed. This command replaces an earlier backup at the same path.

Common service commands:

```bash
sudo systemctl restart xtatech-lora-bridge
sudo systemctl stop xtatech-lora-bridge
sudo systemctl start xtatech-lora-bridge
sudo journalctl -u xtatech-lora-bridge -f
```

Press `Ctrl+C` to stop following the logs.

## 7. Update an existing installation

**Reinstalling overwrites the installed `config.yaml` with the checkout's copy.** First back up the active configuration using the commands above. Then:

```bash
cd "$HOME/Downloads/Xtatech Lora Bridge"
git status --short
git pull --ff-only
sed -i 's/\r$//' install.sh uninstall.sh generate-local-https-cert.sh
```

If Git reports conflicting local edits, resolve or save them before proceeding; do not discard your configuration to force the update. Review any configuration changes introduced by the update, then copy your backed-up configuration into the checkout and incorporate any new settings needed:

```bash
cp "$HOME/xtatech-backups/config.yaml" config.yaml
nano config.yaml
sudo bash install.sh
sudo systemctl status xtatech-lora-bridge --no-pager
```

Existing certificate files are preserved by the installer. Keep credentials in your local configuration and do not commit them to Git.

## 8. Troubleshooting

### `invalid option name`, `pipefail`, or `bash\r` errors

These usually indicate Windows CRLF line endings, or that the script was run with `sh`. From the project folder:

```bash
sed -i 's/\r$//' install.sh
sudo bash install.sh
```

### `User 'user' not found`

The installer could not identify a normal sudo user. Exit the root shell, log in as your regular account, and run `sudo bash install.sh` from there.

### Serial receiver missing or no data

Check the USB cable, receiver power, selected device path, baud rate, and whether the receiver is actually transmitting. Inspect devices and kernel messages:

```bash
ls -l /dev/serial/by-id/
sudo dmesg | tail -n 50
```

To examine raw serial data, stop the bridge first so both programs do not read the receiver at once. Run this after the installation reboot so your login has `dialout` membership:

```bash
sudo systemctl stop xtatech-lora-bridge
/opt/xtatech-lora-bridge/.venv/bin/python /opt/xtatech-lora-bridge/serial_probe.py --port auto --baud 115200 --seconds 30
sudo systemctl start xtatech-lora-bridge
```

For a specific receiver, replace `auto` with its full serial device path. Restart the service even if the probe reports an error.

### MQTT disconnected

Verify the broker address, port, credentials, broker permissions, and network reachability. Test with `mosquitto_sub` as shown above, then inspect the bridge logs. Installing the bridge does not create the MQTT server or its users.

### Web interface unavailable or service fails

Check the machine's current IP address, use HTTPS on port `8088` with the default configuration, and inspect status and logs:

```bash
sudo systemctl status xtatech-lora-bridge --no-pager
sudo journalctl -u xtatech-lora-bridge -n 100 --no-pager
sudo ss -ltnp | grep ':8088'
```

Configuration edits must remain valid YAML. If either configured TLS file is missing, the application logs a warning and starts using HTTP instead. Restore the certificate files or explicitly set both `web.ssl_certfile` and `web.ssl_keyfile` to empty strings if HTTP is intended, then restart the service.

### Machine reboots every 15 minutes

Disable `watchdog.enabled` in `/opt/xtatech-lora-bridge/config.yaml` and restart the service. The supplied watchdog threshold is 900 seconds without serial bytes; increase it if your receiver normally remains silent longer.

## 9. Uninstall

Back up the installed configuration first if you want to retain it. Uninstall removes the installed application directory, including its configuration and certificates:

```bash
cd "$HOME/Downloads/Xtatech Lora Bridge"
sed -i 's/\r$//' uninstall.sh
sudo bash uninstall.sh
```

This stops and disables the service, removes its unit and sudoers rule, removes the Wi-Fi power-saving override, and unmasks the system sleep targets. It keeps the Downloads checkout and installed OS packages. It also leaves the service user's `dialout` membership and any `usbcore.autosuspend=-1` boot option in place.

To also delete the Downloads checkout, use `sudo bash uninstall.sh --purge-downloads` instead. This deletes that source folder and any local edits in it.

### System and data flow

```text
LoRa sensor nodes
    -> LoRa receiver (receiver firmware is external to this repository)
    -> USB/serial, normally 115200 baud, 8N1, no flow control
    -> Python bridge on Linux / Raspberry Pi
    -> MQTT broker
    -> Home Assistant MQTT entities and Lovelace dashboard

Python bridge -> HTTPS web interface, live packets/logs,
                 serial diagnostics, metrics, configuration, service controls
```

The repository implements the serial-to-MQTT gateway and its management interface. LoRa radio settings, transmitter flashing, probe calibration, and receiver firmware must be handled in their respective hardware projects.

- Added automatic serial-port selection and reconnect behavior. Candidate devices, open attempts, raw input, parsed packets, parse drops, and last errors are exposed for diagnosis. Missing serial hardware leaves the application running and retrying.
- Added JSON extraction, automatic key/value parsing, and explicit raw mode. Numeric and boolean key/value fields are converted where supported. The default maximum processed line length is 4096 characters.

- Added live packet/log WebSocket streams, bounded in-memory packet and log buffers (defaults: 300 and 800), latest-node data, node removal, and sorted node display. These buffers are not persistent historical storage.
- Added web configuration view/save/apply, service restart, system reboot, SSH status, system metrics, and a local shell terminal with its own token and session limit.
- Added CPU/load/temperature, memory/swap, disk, network, process, and Raspberry Pi throttling metrics where the host supports them.
- Added repository download/update and install controls with progress reporting. Install eligibility compares the Downloads checkout against the expected repository HEAD and the installed commit marker.

### Unknown-node filtering fix

Serial packets with a blank or case-insensitive `unknown` derived ID are rejected before discovery, state publication, packet storage, and node counting. A separate guard also checks dedicated name fields such as `name`, `node_name`, `node-name`, and `nodeName`, so a valid `ID` cannot bypass a name explicitly set to `unknown`. Node counting has an additional defensive guard.

Rejected lines remain visible in serial diagnostics/logs and count as parse drops. They still represent serial activity; they do not become valid nodes. Explicit raw mode uses the ID `raw`. Old entities or retained messages created before the fix are not automatically removed by this filter.

### MQTT topics and gateway heartbeat

| Topic with current defaults | Content |
| --- | --- |
| `lora/<node_id>/state` | Parsed node JSON including available measurements and timestamps |
| `lora/Aqua101/state` | Above-ground Aqua101 measurements |
| `lora/Lux01/state` | Lux01 measurements |
| `lora/_gateway/pi-zero2-gw01/state` | Gateway heartbeat and health |

Node topics are case-sensitive. The manual YAML was corrected to match capitalized IDs. Changing `mqtt.base_topic`, `mqtt.gateway_id`, or `heartbeat.topic` also requires updating the manual generator/YAML and any dashboard references.

The default heartbeat interval is 30 seconds. The gateway payload includes `gateway_id`, `heartbeat_ts`, `heartbeat_iso`, `uptime_s`, `ip`, `mqtt_connected`, `serial_ok`, `last_serial_rx_ts`, `last_serial_rx_iso`, `nodes_seen`, and `last_serial_error`. Nodes seen is an in-process count of distinct accepted node IDs, not a count of currently online transmitters.

Historical MQTT Explorer evidence supplied on 28 October 2026 showed the gateway connected to MQTT with serial OK, one node seen, and Lux01 publishing readings. This was a historical observation, not a live check performed for this export.

### Measurement update-time fix

The Aqua101 investigation found that unchanged measurements could have old Home Assistant state timestamps while last-seen continued advancing. Added `force_update: true` to node sensors in both the discovery definitions and manual YAML generator/output, allowing repeated identical readings to generate state updates.

Use the payload's `ts_iso` / Last Seen entity to identify the latest received measurement packet. A value's `last_changed` can still remain old when its numeric value is unchanged. This change does not make separate Home Assistant entities update atomically or synchronize a transmitter's internal sampling.

### Lovelace dashboard work

`lovelace-probes.yaml` provides reusable buried-probe and above-ground row templates, compact status/readings, and 24-hour graphs. Aqua101 uses its own air/light row, with temperature, humidity, and lux graphs sized to match the other rows. The probe view also includes gateway connection, serial status, nodes seen, uptime, and heartbeat badges.

The probe rows depend on the custom cards `button-card`, `mini-graph-card`, and `decluttering-card`, plus `card-mod`. Install/register these resources separately in Home Assistant. Merge the templates and desired views into the dashboard's raw YAML configuration.

The supplied file is a broader site dashboard: it also references existing pumps, boreholes, water meters, schedules, trackers, weather equipment, and other entities. Those references do not create those integrations or devices. Scheduler and compass cards require their respective custom resources if those views are retained.

The current probe view has no Lux01 row and omits Aqua08 even though both have MQTT definitions. Add rows using the appropriate templates if needed. Its ONLINE label checks for an available last-seen entity rather than calculating packet age; it is not a reliable stale-node alarm.
